# Спецификация: вкладка «Scorecard» проекта

Еженедельная панель здоровья проекта. Новая вкладка «Scorecard» в ряду вкладок
`Project.tsx`, маршрут `/projects/{id}/scorecard`. Публичная шара — не показывает.

## 1. Определения

- **Неделя** — ISO-неделя в таймзоне проекта (fallback — организации).
- **Дата окончания задачи** — `start_date + duration_days` по календарю проекта (как в Ганте).
- **Просрочена** — статус ≠ `done` и дата окончания < даты расчёта.
- Считаются только задачи живого плана (без неутверждённых предложений).
- Дни везде рабочие (через `project_calendar`).

## 2. Миграции

Поля `Task`: `done_at` (ставится мутацией при переходе в `done`, чистится при
возврате), `in_progress_since` (аналогично для `in_progress`). Бэкфилл из
`revisions`, где возможно.

Таблицы:

- `scorecard_metrics` — конфиг **на проект** (никаких настроек уровня
  организации нет): `project_id + metric_key` uniq, `owner_user_id`
  (nullable, SET NULL), `target_value` numeric, `direction` (`lte|gte`),
  `warn_value` (nullable, в MVP не используется), `enabled`, `position`.
  Дефолты §3 — только сид при первом открытии скоркарда проекта (владельцы
  пустые); дальше владелец, цель и enabled правятся PATCH-ем и действуют
  только в своём проекте.
- `scorecard_snapshots` — снимок: `project_id + metric_key + week_start` uniq
  (понедельник), `value` (nullable = нет данных), `target_value`, `direction`
  (копия конфига на момент снимка), `status` (`ok|warn|risk|no_data`),
  `computed_at`, `computed_by` (nullable = планировщик), `details` JSONB
  (сериализованный drill-down: id и краткие атрибуты задач метрики).
  **Снимки прошлых недель неизменяемы; пересчитывается только текущая неделя.**
- `scorecard_alerts` — `project_id`, `metric_key`, `week_start`,
  `kind` (`rule_triggered|metric_risk`), `payload` JSONB, `created_at`,
  `resolved_at` (nullable).

## 3. Метрики

| `metric_key` | Формула | Цель по умолч. |
|---|---|---|
| `overdue_tasks` | число просроченных задач | ≤ 2 |
| `avg_overdue_days` | средняя просрочка просроченных, раб. дней; 0 если нет | ≤ 3 |
| `date_shifts` | операций в `revisions` за неделю, изменивших `start_date`/`duration_days` на ≥ `resolve_shift_threshold` | ≤ 5 |
| `close_rate` | done за неделю ÷ задач с датой окончания в этой неделе; 1,0 при 0/0 | ≥ 1,0 |
| `stale_in_progress` | задач в `in_progress` > 5 раб. дней | ≤ 3 |
| `unassigned_tasks` | задач без исполнителя (кроме вех) | ≤ 0 |
| `daily_health` | средний балл дейли недели, 0–10. **Модуля дейли нет — метрика в `no_data`, скрыта до его появления** | ≥ 8,0 |
| `data_quality` | (1 − непригодных/всех) × 100%. Непригодна: нет исполнителя, ИЛИ «нереальный срок» — просрочена > 10 раб. дней без единой правки дат в `revisions`, либо создана AI (`created_by_ai_session_id`) и даты не правились | ≥ 90% |

Направление фиксировано ключом. Цель, владелец и enabled — настройки
конкретного проекта; колонка «Цель по умолч.» — лишь сид новых проектов.

## 4. Статусы, серии, правило

- Статус: **ok** — факт удовлетворяет цели; **risk** — хуже порога (цель × 2
  для `lte`, при цели 0 — значение > 2; цель × 0,75 для `gte`); **warn** —
  между; **no_data** — выключена/нет источника (серый прочерк, в серии и
  правилах не участвует). Множители — константы MVP.
- Серия — недель подряд (включая текущую) в текущем статусе; считается по
  снимкам при чтении; в бейдже с 2: «Риск · 3 нед.».
- Правило «красная 2 недели подряд»: при записи снимка, если текущая и прошлая
  недели — `risk`, и для этой серии событие ещё не создавалось: (1) через слой
  мутаций создаётся задача «Разобрать: {метрика}», исполнитель — владелец
  метрики, срок — конец недели, категория — первая в проекте; (2) пишется
  `rule_triggered` со ссылкой на задачу. Повтор подавляется до разрыва серии.
- `metric_risk`-события: метрики в `risk` на текущей неделе; активны, пока
  статус `risk`.

## 5. Снимки и пересчёт

- Планировщика нет — **ленивая фиксация**: первый GET после границы недели
  идемпотентно дозаписывает недостающие недельные снимки (транзакция на
  неделю), затем считает текущую. Пропущенные недели: метрики 3–4 точно по
  журналу; срезы (1, 2, 5, 6, 8) по текущему состоянию с `backfilled: true` в
  `details`.
- «Пересчитать» — POST, только текущая неделя (значения, статусы, details,
  правила); право записи; rate limit 1/мин на проект.
- Текущая неделя при GET считается вживую с кэшем 5 минут.
- Окно истории: 13 недель, селектор статичен (API уже принимает `weeks`).

## 6. API

Чтение — кто видит проект; запись — право записи. OpenAPI + `gen:api`.

- `GET /projects/{id}/scorecard?weeks=13` → `week` (номер, диапазон),
  `computed_at`, `metrics[]` (конфиг + текущее значение/статус/серия +
  `history[]`), `alerts[]` (для `metric_risk` по `overdue_tasks` — топ-3 задач:
  id, название, исполнитель, дни просрочки), `daily: null` (контракт:
  `held/planned`, `avg_score`, `by_day[]`, `blockers`), `data_quality`
  (счётчики причин). Побочный эффект — ленивая фиксация.
- `POST /projects/{id}/scorecard/recalculate` → тот же ответ.
- `PATCH /projects/{id}/scorecard/metrics/{key}` — owner, target, enabled.
- `GET /projects/{id}/scorecard/metrics/{key}/tasks?week=` — прошлые недели из
  `details` снимка, текущая — живой расчёт.

## 7. UI

Модуль `frontend/src/scorecard/` (компонент + css + react-query-хук, по
образцу соседей). Northstar-палитра; статусные цвета — как у статусов Ганта.
Две колонки 2/3 + 1/3; ниже ~1100px правая уходит вниз; таблица скроллится
горизонтально. Все строки через i18n (ru/en/az). Десятичные — с запятой в ru.

**Шапка:** «Scorecard проекта»; подзаголовок «Неделя N · дд–дд месяц ·
обновлено …» (из `computed_at`); кнопки «13 недель» (статична) и
«Пересчитать» (primary, право записи, disabled оффлайн).

**Таблица** — колонки: метрика (название + аватар-инициал и имя владельца,
«не назначен»), «факт / цель» (факт в цвете статуса, знак ≤/≥), спарклайн
(див-столбики или инлайн-SVG без библиотек: столбик на неделю в цвете статуса
недели, пустой при no_data; тултип: неделя, значение, статус), бейдж статуса
(+ «· N нед.» при серии ≥ 2). Строки `risk` — красная левая кромка + розовая
подложка. Клик по строке/столбику — drill-down (панель или разворот строки) со
списком задач за неделю; клик по задаче — панель задачи на Ганте. С правом
записи: владелец — выбор из участников, цель — числовое поле; PATCH,
оптимистично.

**Правая колонка:**
- «Требует внимания» + счётчик активных событий. Карточка правила — текст и
  ссылка на созданную задачу; карточка риск-метрики — топ-3 задач и «Открыть
  все N задач →». Пусто — «Всё в норме».
- «Дейли за неделю» — в MVP скрыта. Контракт вёрстки: бейдж «X из Y», средний
  балл крупно, гистограмма пн–пт по баллу, строка блокеров с красной плашкой
  о зависшем.
- «Качество данных проекта» — %, прогресс-бар в цвете статуса, расшифровка
  «у N задач нет реальных сроков, у M — нет исполнителя».

**Состояния:** загрузка — скелет; ошибка — как на экране проекта; первая
неделя без истории — валидна (спарклайн из одного столбика).

**Тесты:** бэкенд — каждая метрика и статусы (границы недель, таймзоны),
идемпотентность фиксации, подавление повтора правила, неизменяемость прошлых
снимков; фронт — vitest + msw: рендер по фикстуре, drill-down, PATCH.

## 8. Этапность

MVP: миграции; метрики 1–6, 8; статусы/серии/фиксация/«Пересчитать»/правило;
API; вкладка + таблица + спарклайны + drill-down + карточки «Требует
внимания» и «Качество данных» + редактирование владельца/цели.

После MVP: `daily_health` и карточка дейли (с модулем дейли), ключи задач
(`AUR-142` из макета — в MVP задачи без ключа), окно 26/52, настройка порогов
warn/risk, выделенный планировщик, скоркард в публичной шаре.

## 9. Открытые вопросы

1. Вводить ли ключи задач.
2. Эвристика «нереальных сроков» (§3) — принять или заменить явным признаком
   «даты подтверждены».
3. Категория автозадачи правила: первая или служебная «Scorecard».
4. Рендер «0 / 0» у `unassigned_tasks` не должен читаться как деление.
5. Живой расчёт текущей недели при GET (принято, кэш 5 мин) или только по
   «Пересчитать»/границе недели.
