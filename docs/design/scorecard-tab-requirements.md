# Требования: вкладка «Scorecard» проекта

Разбор макета скоркарда и требования к разработке. Макет показывает новую
вкладку проекта — «Scorecard» — рядом с существующими вкладками. Это
еженедельная панель здоровья проекта: восемь метрик с целями и владельцами,
история за 13 недель, автоматические правила эскалации и сводка дейли.

Документ — источник требований для реализации. Он разделяет то, что макет
рисует, то, что уже поддержано моделью данных, и то, чего в системе пока нет.

---

## 1. Что нарисовано в макете

### 1.1. Навигация и шапка

- Вкладки проекта в макете: **Гант · Задачи · Команда · Scorecard · Дейли**.
  Сейчас в приложении вкладки другие (Гант · Предложения · История), поэтому
  требование — добавить «Scorecard» в существующий ряд вкладок
  (`Project.tsx`, маршрут `/projects/{id}/scorecard`), а не воспроизводить
  ряд из макета.
- Заголовок «Scorecard проекта».
- Подзаголовок-контекст: **«Неделя 32 · 4–10 августа · обновлено в
  понедельник, 09:00»** — номер ISO-недели, её диапазон дат и момент
  последнего расчёта.
- Справа два действия:
  - **«13 недель»** — селектор глубины истории (окно спарклайнов);
  - **«Пересчитать»** — primary-кнопка ручного пересчёта текущей недели.

### 1.2. Таблица метрик (левая, основная зона)

Колонки: **Метрика** (название + владелец с аватаром), **Факт / Цель**,
**13 недель** (мини-гистограмма по неделям), **Статус** (бейдж).

Строки макета, сверху вниз:

| # | Метрика | Владелец | Факт / Цель | Статус |
|---|---|---|---|---|
| 1 | Просроченные задачи | Дима | 5 / ≤2 | Риск |
| 2 | Средняя просрочка, дней | Дима | 4,5 / ≤3 | Внимание |
| 3 | Сдвиги сроков за неделю | Лена | 14 / ≤5 | **Риск · 3 нед.** |
| 4 | Скорость закрытия | Лена | 0,8 / ≥1,0 | Внимание |
| 5 | В работе дольше 5 дней | Игорь | 2 / ≤3 | Норма |
| 6 | Задачи без исполнителя | Анна | 0 / 0 | Норма |
| 7 | Здоровье дейли | Лена | 8,4 / ≥8,0 | Норма |
| 8 | Качество данных | Анна | 78% / ≥90% | Внимание |

Что макет сообщает деталями:

- **Три статуса**: Норма (зелёный), Внимание (янтарный), Риск (красный).
  Значение «факт» окрашено в цвет статуса; у цели знак направления
  (`≤` — «меньше лучше», `≥` — «больше лучше»).
- **Строки в статусе «Риск» выделены**: красная левая кромка и розовая
  подложка всей строки.
- **Серия недель в статусе**: бейдж «Риск · 3 нед.» показывает, сколько
  недель подряд метрика в текущем статусе.
- **Спарклайн** — по одному столбику на неделю окна; каждый столбик окрашен
  в цвет статуса своей недели (виден переход зелёный → янтарный → красный).
- **Подвал таблицы**, две подписи-обещания:
  - «Клик по метрике открывает задачи, из которых она сложилась» —
    у каждой метрики есть drill-down до списка задач;
  - «Снимок за неделю · правки задним числом не меняют историю» —
    недельные значения фиксируются снимком и неизменяемы.

### 1.3. Правая колонка

Три карточки:

1. **«Требует внимания»** со счётчиком (2) — лента эскалаций:
   - карточка метрики «Сдвиги сроков за неделю»: «Третью неделю в красном.
     Сработало правило „красная 2 недели подряд“» и след автоматики —
     «Создана задача „Разобрать сроки“». То есть у скоркарда есть **правила**,
     которые по условию создают задачу в проекте и пишут об этом в ленту.
   - карточка «Просроченные задачи · 5 задач» с тремя худшими задачами
     (ключ вида `AUR-142`, название, аватар исполнителя, просрочка «+6 д»)
     и ссылкой «Открыть все 5 задач →».
2. **«Дейли за неделю»** с бейджем «5 из 5» (проведено встреч из плановых):
   крупный средний балл «8,4 / 10», гистограмма пн–пт с окраской по баллу
   дня, строка «Блокеры: 4 из 6 закрыто» и красная плашка «один висит
   3-й день».
3. **«Качество данных проекта»** — 78%, прогресс-бар и расшифровка:
   «У 14 задач нет реальных сроков, у 3 — нет исполнителя. Остальное
   читайте с поправкой» — метрика №8 продублирована карточкой с объяснением,
   почему остальным цифрам можно верить лишь с оговоркой.

## 2. Понятия и модель данных

### 2.1. Новые сущности

**Конфигурация метрики** (`scorecard_metrics`) — по строке на метрику проекта:

- `project_id`, `metric_key` (enum из §3), уникальны вместе;
- `owner_user_id` — владелец метрики (nullable, SET NULL при удалении);
- `target_value` (numeric) и `direction` (`lte` | `gte`) — цель и знак;
- `warn_value` (numeric, nullable) — порог «Внимание» (см. §4.1);
- `enabled` — метрику можно выключить;
- `position` — порядок строк.

При первом открытии скоркарда проекта конфигурация создаётся из дефолтов
(§3, колонка «Цель по умолчанию»); владельцы не заполняются.

**Недельный снимок** (`scorecard_snapshots`) — по строке на метрику на неделю:

- `project_id`, `metric_key`, `week_start` (date, понедельник ISO-недели),
  уникальны вместе;
- `value` (numeric, nullable — «нет данных»), `target_value`, `direction`
  (цель копируется в снимок: смена цели задним числом не перекрашивает
  историю);
- `status` (`ok` | `warn` | `risk` | `no_data`) — вычислен при записи;
- `computed_at`, `computed_by` (nullable: null — планировщик, иначе — кто
  нажал «Пересчитать»);
- `details` (JSONB) — сериализованный drill-down на момент снимка: id и
  краткие атрибуты задач, из которых сложилось значение. Именно он делает
  обещание «правки задним числом не меняют историю» выполнимым: список
  задач прошлой недели читается из снимка, а не пересчитывается по живым
  данным.

**Правило неизменяемости.** Снимки прошлых недель никогда не
перезаписываются. Пересчитывать (по расписанию или кнопкой) можно только
снимок текущей недели.

**Событие внимания** (`scorecard_alerts`) — лента «Требует внимания»:

- `project_id`, `metric_key`, `week_start`, `kind`
  (`rule_triggered` | `metric_risk`), `payload` (JSONB: текст-контекст,
  id созданной задачи), `created_at`, `resolved_at` (nullable).

### 2.2. Чего в модели данных нет — и что с этим делать

Разбор макета упирается в четыре разрыва с текущей схемой. Каждый требует
решения до начала реализации; предлагаемые решения — ниже.

1. **Нет момента завершения задачи.** У `Task` есть `status`, но нет
   `done_at`, поэтому «Скорость закрытия» (закрыто за неделю) напрямую не
   считается. *Решение:* добавить `Task.done_at` (заполняется мутацией при
   переходе в `done`, очищается при возврате), для «В работе дольше N дней» —
   аналогично `in_progress_since`. Бэкфилл по журналу `revisions`, где это
   возможно.
2. **Нет человекочитаемых ключей задач** (`AUR-142` в макете). *Решение
   MVP:* показывать задачи без ключа (название + категория). Введение ключей
   задач — отдельная работа вне рамок скоркарда.
3. **Нет модуля «Дейли».** Метрика «Здоровье дейли» и карточка «Дейли за
   неделю» (баллы встреч, блокеры) требуют несуществующей вкладки «Дейли».
   *Решение:* контракт метрик закладывается сразу, но метрика №7 и карточка
   дейли в MVP скрыты (метрика в состоянии «нет данных»), появляются вместе
   с модулем дейли.
4. **«Нет реальных сроков» не выражается схемой напрямую:** `start_date` и
   `duration_days` у задачи NOT NULL — «без сроков» задач не бывает.
   *Решение:* определить «нереальный срок» эвристикой (см. §3, метрика 8) и
   зафиксировать её в документации к метрике; эвристика уточняется без
   миграций, потому что живёт в расчёте.

Опорные существующие механизмы: журнал `revisions` (даёт «Сдвиги сроков за
неделю»), `resolve_shift_threshold` (порог значимого сдвига уже есть в
настройках проекта/организации), `task_assignees`, календарь проекта
(`project_calendar`) для расчётов в рабочих днях, таймзона проекта — для
границ недели и времени снимка.

## 3. Каталог метрик

Общие определения:

- **Неделя** — ISO-неделя в таймзоне проекта (fallback — таймзона
  организации). Все «за неделю» — интервал [понедельник 00:00; следующий
  понедельник 00:00).
- **Дата окончания задачи** — вычисляемая: `start_date` + `duration_days`
  по календарю проекта (как в Ганте).
- **Просрочена** — задача не в статусе `done`, не веха-черновик, и её дата
  окончания раньше даты расчёта.
- Из расчётов исключаются задачи неутверждённых предложений; считаются
  только задачи живого плана.

| # | `metric_key` | Определение | Цель по умолчанию | Источник данных |
|---|---|---|---|---|
| 1 | `overdue_tasks` | Число просроченных задач на момент снимка | ≤ 2 | `tasks` |
| 2 | `avg_overdue_days` | Средняя просрочка по просроченным задачам, в рабочих днях; 0 при отсутствии просроченных | ≤ 3 | `tasks` + календарь |
| 3 | `date_shifts` | Число значимых сдвигов сроков за неделю: операций из `revisions`, изменивших `start_date`/`duration_days` задачи не меньше, чем на порог `resolve_shift_threshold` | ≤ 5 | `revisions` |
| 4 | `close_rate` | Скорость закрытия: задач переведено в `done` за неделю ÷ задач, чья дата окончания попадала в эту неделю; 1,0 при нулевом знаменателе и нулевом числителе | ≥ 1,0 | `tasks.done_at` (новое поле) |
| 5 | `stale_in_progress` | Задач в `in_progress` дольше 5 рабочих дней | ≤ 3 | `tasks.in_progress_since` (новое поле) |
| 6 | `unassigned_tasks` | Задач без единого исполнителя (кроме вех) | = 0 | `task_assignees` |
| 7 | `daily_health` | Средний балл дейли-встреч недели, 0–10 | ≥ 8,0 | модуль «Дейли» (нет; метрика скрыта до его появления) |
| 8 | `data_quality` | Доля задач, пригодных для честной отчётности, % | ≥ 90% | `tasks`, `task_assignees` |

**Метрика 8, расшифровка.** Задача «непригодна», если выполняется хотя бы
одно: (а) нет исполнителя; (б) срок «нереальный» — задача просрочена больше
чем на 10 рабочих дней и её даты ни разу не правились после создания
(признак: нет записей о сдвиге в `revisions`), либо задача создана
AI-сессией (`created_by_ai_session_id`) и её даты ни разу не подтверждались
правкой. Значение = (1 − непригодных/всех) × 100%. Карточка «Качество данных
проекта» показывает раздельные счётчики причин («у N задач нет реальных
сроков, у M — нет исполнителя»).

Направление у всех метрик фиксировано ключом (не настраивается), цель —
настраивается на проект.

## 4. Статусы, серии и правила

### 4.1. Вычисление статуса

- **Норма** — факт удовлетворяет цели (`value ≤ target` при `lte`,
  `value ≥ target` при `gte`).
- **Риск** — факт хуже порога риска. Порог риска по умолчанию: цель × 2 для
  `lte` (для цели 0 — любое значение > 2), цель × 0,75 для `gte`.
- **Внимание** — между ними.
- **Нет данных** — метрика выключена или источник недоступен (например,
  `daily_health` без модуля дейли): серый прочерк, в спарклайне — пустой
  столбик, в серии и правилах не участвует.

Пороговые множители — константы MVP; `warn_value` в конфигурации оставлен,
чтобы позже открыть их настройку без миграции.

### 4.2. Серия («Риск · 3 нед.»)

Серия — число последних подряд идущих недель (включая текущую), в которых
статус метрики совпадает с текущим. Показывается в бейдже начиная с 2:
«Риск · 3 нед.», «Внимание · 2 нед.». Считается по снимкам при чтении, не
хранится.

### 4.3. Правила эскалации

MVP включает одно встроенное правило, показанное в макете:

**«Красная 2 недели подряд».** При записи снимка (планового или ручного):
если метрика в статусе «Риск» и прошлая неделя тоже была «Риск», а событие
для этой серии ещё не создавалось, то:

1. создаётся задача в проекте: название «Разобрать: {название метрики}»,
   исполнитель — владелец метрики, срок — конец текущей недели, категория —
   первая в проекте; создание идёт через существующий слой мутаций (журнал,
   undo, live-обновления — бесплатно);
2. пишется событие `rule_triggered` в `scorecard_alerts` со ссылкой на
   созданную задачу.

Повторное срабатывание той же серии подавляется, пока серия не прервётся
(неделя не в «Риске»). Кроме правила, в ленту «Требует внимания» попадают
метрики в статусе «Риск» текущей недели (kind `metric_risk`, живёт пока
статус — «Риск»): в макете именно так показаны «Просроченные задачи».

Счётчик на карточке «Требует внимания» — число активных событий.

## 5. Снимки: расписание, «Пересчитать», окно истории

- **Плановый снимок** — раз в неделю, понедельник 09:00 в таймзоне проекта,
  фиксирует **прошедшую** неделю и открывает текущую. В бэкенде сейчас нет
  планировщика, поэтому MVP делает **ленивую фиксацию**: первый запрос
  скоркарда после границы недели дозаписывает недостающие недельные снимки
  (по одной транзакции на неделю, идемпотентно), после чего считает текущую.
  Подпись «обновлено …» берётся из `computed_at` снимка текущей недели.
  Выделенный планировщик (cron-контейнер / APScheduler) — отдельное решение
  вне MVP; ленивая фиксация остаётся корректной при его появлении.
- **«Пересчитать»** — POST-запрос, пересчитывает только текущую неделю
  (значения, статусы, drill-down, правила). Доступна ролям с правом записи
  в проект. Ограничение частоты: не чаще раза в минуту на проект.
- **Пропущенные недели** (проект не открывали) фиксируются задним числом при
  ленивой фиксации — по состоянию `tasks`/`revisions` на границу той недели,
  где это восстановимо (метрики 3, 4 — точно, по журналу; метрики-срезы
  1, 2, 5, 6, 8 — по текущему состоянию с пометкой `backfilled: true` в
  `details`).
- **Окно истории**: селектор «13 недель» — MVP фиксирует одно значение,
  13 недель; элемент рисуется как статичный. Расширение (26/52) — после MVP;
  API принимает `weeks` уже сейчас.

## 6. API

Все маршруты — под существующей авторизацией проекта; чтение доступно
любому, кто видит проект, запись — по праву записи.

- `GET /projects/{id}/scorecard?weeks=13` — один ответ на всю вкладку:
  - `week` (текущая: номер, диапазон дат), `computed_at`;
  - `metrics[]`: конфигурация (ключ, владелец, цель, направление, enabled)
    + текущее значение, статус, серия + `history[]` (неделя, значение,
    статус) на глубину окна;
  - `alerts[]` — активные события «Требует внимания» (+ 3 худшие задачи для
    `metric_risk` по `overdue_tasks`: id, название, исполнитель, дни
    просрочки);
  - `daily` — null, пока модуля дейли нет (контракт: `held`/`planned`,
    `avg_score`, `by_day[]`, `blockers`);
  - `data_quality` — расшифровка для карточки (счётчики причин).
  Побочный эффект — ленивая фиксация недель (§5).
- `POST /projects/{id}/scorecard/recalculate` — пересчёт текущей недели,
  возвращает тот же ответ, что GET.
- `PATCH /projects/{id}/scorecard/metrics/{metric_key}` — владелец, цель,
  enabled.
- `GET /projects/{id}/scorecard/metrics/{metric_key}/tasks?week=` —
  drill-down: список задач метрики; для прошлых недель — из `details`
  снимка, для текущей — живой расчёт.

OpenAPI обновляется (`openapi.json`), фронтовые типы — через `gen:api`.

## 7. Требования к интерфейсу

### 7.1. Каркас

- Маршрут `/projects/{id}/scorecard`, пункт «Scorecard» в ряду вкладок
  `Project.tsx`; экран — `frontend/src/scorecard/` по образцу соседних
  модулей: компонент, css, хук запроса на react-query.
- Публичная шара проекта скоркард **не** показывает (MVP).
- Вёрстка: две колонки (таблица ~2/3, правая колонка ~1/3); ниже
  ~1100px правая колонка уходит под таблицу; таблица на узких экранах
  скроллится по горизонтали. Стилистика — палитра и типографика
  northstar-темы (статусные цвета — те же, что у статусов Ганта:
  зелёный/янтарный/красный).

### 7.2. Таблица

- Строка: название метрики + владелец (аватар-инициал + имя; «не назначен»,
  если владельца нет), «факт / цель» (факт окрашен статусом; десятичные — с
  запятой в ru-локали, форматирование через существующий i18n-слой), спарклайн,
  бейдж статуса (с «· N нед.» при серии ≥ 2).
- Строки «Риск» — левая красная кромка + розовая подложка (как в макете).
- Спарклайн: столбик на неделю, цвет — статус недели, пустой столбик — нет
  данных; тултип столбика: неделя, значение, статус. Реализация — див-столбики
  или инлайн-SVG, без графических библиотек.
- Клик по строке открывает drill-down (панель или разворот строки) со
  списком задач метрики за выбранную неделю; клик по задаче ведёт к задаче
  (открытие панели задачи на Ганте). Клик по столбику спарклайна — тот же
  drill-down за ту неделю.
- Редактирование (право записи): владелец — выбор из участников проекта,
  цель — числовое поле; изменения через PATCH, оптимистично.

### 7.3. Правая колонка

- «Требует внимания»: счётчик активных событий; карточка правила — текст
  («Третью неделю в красном. Сработало правило „красная 2 недели подряд“»)
  и ссылка на созданную задачу; карточка риск-метрики — топ-3 задач и
  «Открыть все N задач →» в полный drill-down. Пустое состояние — карточка
  скрыта или «Всё в норме».
- «Дейли за неделю»: в MVP скрыта (данных нет). Контракт вёрстки по макету:
  бейдж «X из Y», средний балл крупно, гистограмма пн–пт с окраской по
  баллу, строка блокеров с красной плашкой о зависшем.
- «Качество данных проекта»: процент, прогресс-бар в цвете статуса,
  текст-расшифровка со счётчиками причин.

### 7.4. Состояния и качество

- Загрузка — скелет таблицы; ошибка — по общему образцу экрана проекта;
  оффлайн — данные из кэша react-query, «Пересчитать» задизейблена.
- Первое открытие проекта без истории: таблица с текущими значениями,
  спарклайны из одной недели — это валидное состояние, не ошибка.
- Все строки — через i18n (ru/en/az), никаких зашитых русских строк.
- Тесты: расчёт каждой метрики и статусов (бэкенд, включая границы недель и
  таймзоны), идемпотентность ленивой фиксации, подавление повторного
  срабатывания правила, неизменяемость прошлых снимков; фронт — рендер
  таблицы по фикстуре ответа, drill-down, PATCH владельца/цели
  (vitest + msw, по образцу соседних экранов).

## 8. Этапность

**MVP (одна очередь работ):**

1. Миграции: `done_at`/`in_progress_since` у задач + три новые таблицы
   (`scorecard_metrics`, `scorecard_snapshots`, `scorecard_alerts`).
2. Расчёт метрик 1–6 и 8; статусы, серии, ленивая фиксация, «Пересчитать»,
   правило «красная 2 недели подряд».
3. GET/POST/PATCH/drill-down API + OpenAPI.
4. Вкладка, таблица, спарклайны, drill-down, карточки «Требует внимания» и
   «Качество данных», редактирование владельца/цели.

**После MVP:** метрика «Здоровье дейли» и карточка «Дейли за неделю»
(вместе с модулем дейли), человекочитаемые ключи задач, селектор глубины
окна (26/52), настройка порогов «Внимание/Риск», выделенный планировщик
снимков, скоркард в публичной шаре.

   Предложение MVP: живой расчёт текущей недели при GET с кэшем на 5 минут.
